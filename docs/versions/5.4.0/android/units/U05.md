## Flows

### F-U05-01 Add a subscription URL

1. **start**: actor: opens Subscriptions from the navigation drawer.
2. **step**: actor: taps Add a subscription.
3. **step**: system: shows Edit subscription with an empty field, a parse error and OK disabled.
4. **step**: actor: types a URL.
5. **decision**: does the text parse as a URL? Decision exits: yes: the actor taps OK. No: the flow ends, OK stays disabled and the error stays.
6. **step**: actor: taps OK.
7. **end**: system: inserts the URL in sorted order, persists it and scrolls to it.
8. **end**: OK stays disabled and the error stays.
9. **end (exception exit)**: actor: taps Cancel. The list is unchanged.

Exception exits:
- Cancel dismisses the dialog with no result.
- An empty field is malformed, so OK is disabled from the first frame.

### F-U05-02 Edit one subscription URL

1. **start**: actor: taps a subscription row.
2. **step**: system: shows Edit subscription with the URL prefilled, OK enabled and Remove visible.
3. **step**: actor: changes the URL text.
4. **decision**: does the edited text parse as a URL? Decision exits: yes: the actor taps OK. No: the flow ends and OK stays disabled.
5. **step**: actor: taps OK.
6. **end**: system: removes the old URL, inserts the edited URL in sorted order, persists and scrolls to it.
7. **end**: OK stays disabled.
8. **end (exception exit)**: actor: taps Cancel. The stored URL is unchanged.
9. **end**: actor: taps Remove. The removal continues in F-U05-03.

Exception exits:
- Cancel returns no result, so the old URL stays.
- Remove is a separate result that runs the delete path of F-U05-03.

### F-U05-03 Remove a subscription URL with an undo window

1. **start**: actor: swipes a row from the start edge, or taps Remove in Edit subscription.
2. **step**: system: removes the URL from the list and persists at once.
3. **step**: system: shows the removed-items snackbar with Undo.
4. **decision**: does the actor tap Undo before the snackbar dismisses? Decision exits: yes: the system re-adds every removed URL in sorted order and persists. No: the snackbar dismisses and the deletion stands.
5. **step**: system: re-adds every removed URL in sorted order and persists.
6. **end**: the subscription is back in the list.
7. **end**: the snackbar dismisses and the deletion stands.
8. **end (exception exit)**: actor: leaves the screen. onDetach flushes the snackbar and the deletion stands.

Exception exits:
- Leaving the screen dismisses the snackbar and keeps the deletion.
- Undo restores a URL that the store no longer lists.

### F-U05-04 Refresh all subscriptions

1. **start**: actor: taps Refresh servers from subscription, or an explicit start intent reaches SubscriptionService.
2. **decision**: is SubscriptionService.idle true? Decision exits: yes: the system starts the service and posts the progress notification with a determinate bar of 0 of N. No: the second start stops the service and the active run ends.
3. **step**: system: starts the service and posts the progress notification with a determinate bar of 0 of N.
4. **step**: system: fetches every stored URL in parallel and advances the determinate bar as each download ends.
5. **step (decision exit)**: did a download throw an exception? Yes: the system shows a long toast and keeps no body for that URL. No: the system keeps the downloaded body.
6. **step**: system: shows a long toast and keeps no body for that URL.
7. **step**: system: keeps the downloaded body.
8. **step**: system: after every download ends, sets the title to Finishing up… with an indeterminate bar.
9. **step**: system: preprocesses the stored profiles and marks every Active non-user profile Obsolete.
10. **step (decision exit)**: does a body raise a JSON parse error? Yes: the system shows a long toast and skips only that body. No: the system merges the parsed profiles by name and address.
11. **step**: system: shows a long toast and skips only that body.
12. **step**: system: merges the parsed profiles by name and address.
13. **step**: system: writes the queued profiles and cancels the notification.
14. **end**: idle returns to true and the profile list reloads only if the Profiles screen is attached.
15. **step (exception exit)**: system: the second start stops the service and the active run ends.
16. **end (exception exit)**: the active run is cancelled, no profile is written and idle returns to true.

Exception exits:
- A download that fails is skipped after a long toast. The run continues and the profiles of that URL become Obsolete.
- A body that raises a JSON parse error is skipped after a long toast. The other bodies still merge.
- A run with no stored URL or with every download failed still obsoletes every Active non-user profile.
- Stop cancels the run through F-U05-05.

### F-U05-05 Stop a running refresh

1. **start**: actor: taps Stop in the Subscription Service notification.
2. **step**: system: the Action.ABORT broadcast reaches the registered receiver.
3. **decision**: is the run still fetching? Decision exits: yes: worker.cancel() cancels the coroutine before profiles are created. No: the merge in Finishing up runs to completion.
4. **step**: system: worker.cancel() cancels the coroutine before profiles are created.
5. **step**: system: the merge in Finishing up runs to completion.
6. **step**: system: the profiles are created and written, then the finally block cancels the notification and sets idle true.
7. **end**: system: the finally block deletes temp files, cancels the notification and sets idle true.
8. **end (exception exit)**: no refresh is running, so no receiver is registered and nothing happens.

Exception exits:
- The receiver exists only while a run is active, so Stop outside a run has no effect.
- Stop during Finishing up cannot interrupt the merge, which has no suspension point.

### F-U05-06 Merge fetched profiles into the stored list

1. **start**: system: reads the current profile id and every stored profile.
2. **decision**: is the stored profile user-configured? Decision exits: yes: the flow ends and the profile is left untouched. No: the system indexes it by name plus address.
3. **decision**: is its name-plus-address key already taken? Decision exits: yes: the system deletes the duplicate and resets the selection if it was current. No: the system keeps it.
4. **decision**: is the kept profile Active? Decision exits: yes: the system marks it Obsolete and queues a write. No: the system leaves it as is.
5. **step**: system: for each incoming profile, looks up its name-plus-address key.
6. **decision**: does the key hold an Obsolete profile? Decision exits: yes: the system copies password, method, plugin and UDP fallback, marks the profile Active and queues a write. No: the flow continues to the next decision.
7. **decision**: does the key hold an Active profile? Decision exits: yes: the flow ends, the stored profile is kept and the incoming copy is ignored. No: the system creates the incoming profile as Active.
8. **step**: system: creates the incoming profile as Active.
9. **end**: system: writes every queued profile and calls reloadProfiles on the registered listener.
10. **end**: keep the stored profile and ignore the incoming copy.
11. **end**: leave the profile untouched.

Exception exits:
- A body that raises a JSON parse error is skipped with a long toast.
- The body sequence can be empty. With no stored URL or with every download failed, the preprocessing still marks every Active non-user profile Obsolete.
- The reload reaches only a live ProfilesFragment. ProfileManager.listener is null while the Subscriptions screen is open, so the call does nothing.
