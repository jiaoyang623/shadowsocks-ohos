## Flows

### F-U02-01 Select a profile

1. **start**: start: user opens the Profiles screen. Next: list: shows active profiles in ascending userOrder.
2. **step**: list: shows active profiles in ascending userOrder. Next: decision: row tap enabled?
3. **decision**: decision: row tap enabled? yes → user taps a row, no → the tap has no effect. Decision exit: Yes → user: taps a row. No → end: the tap is ignored and nothing changes.
4. **step**: user: taps a row. Next: system: Core.switchProfile writes DataStore.profileId.
5. **step**: system: Core.switchProfile writes DataStore.profileId. Next: system: refreshId(old) rebinds the old row, and the tapped row is marked selected without a rebind.
6. **step**: system: refreshId(old) rebinds the old row, and the tapped row is marked selected without a rebind. Next: decision: service can stop?
7. **decision**: decision: service can stop? yes → broadcast a reload, no → no service runs. Decision exit: Yes → system: Core.reloadService sends Action.RELOAD. No → end: the choice is stored and no service runs.
8. **step**: system: Core.reloadService sends Action.RELOAD. Next: end: the tunnel reloads with the selected profile.
9. **end**: end: the tunnel reloads with the selected profile.
10. **end**: end: the choice is stored and no service runs.
11. **end**: end: the tap is ignored and nothing changes.

Exception exits:

- The service state is Idle or Stopping, so no row accepts a tap.
- The selected profile id has no row, so no row shows the selected mark.
- The tapped row's profile was deleted elsewhere, so Core.switchProfile creates a blank profile and selects it.

### F-U02-02 Filter the profile list

1. **start**: start: user taps the Search toolbar action. Next: system: SearchView expands.
2. **step**: system: SearchView expands with the hint Search. Next: user: types a query.
3. **step**: user: types a query. Next: decision: query empty?
4. **decision**: decision: query empty? yes → show all profiles, no → filter the list. Decision exit: Yes → system: show every profile in userOrder. No → system: filter by name and host.
5. **step**: system: show every profile in userOrder. Next: list: rows update with the filtered set.
6. **step**: system: filter keeps profiles whose name or host contains the query, ignoring case. Next: list: rows update with the filtered set.
7. **step**: list: rows update with the filtered set. Next: decision: any profile matches?
8. **decision**: decision: any profile matches? yes → matches shown, no → empty list shown. Decision exit: Yes → end: matching rows are shown. No → end: the list shows no rows and the selected id is unchanged.
9. **end**: end: matching rows are shown and the selected id is unchanged.
10. **end**: end: the list shows no rows and the selected id is unchanged.

### F-U02-03 Reorder profiles by drag

1. **start**: start: user long-presses a profile row. Next: decision: drag enabled?
2. **decision**: decision: drag enabled? yes → the row lifts, no → nothing happens. Decision exit: Yes → user: drags the row across another row. No → end: no drag starts.
3. **step**: user: drags the row across another row. Next: system: ItemTouchHelper.onMove calls ProfilesAdapter.move, whose first line flushes the undo snackbar.
4. **step**: system: ItemTouchHelper.onMove calls ProfilesAdapter.move, whose first line flushes the undo snackbar. Next: system: move rotates userOrder across the range.
5. **step**: system: ProfilesAdapter.move rotates userOrder across the moved range. Next: user: drops the row.
6. **step**: user: drops the row. Next: system: commitMove calls ProfileManager.updateProfile for each changed profile.
7. **step**: system: commitMove calls ProfileManager.updateProfile for each changed profile. Next: decision: database update succeeds?
